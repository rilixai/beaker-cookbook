This is the operating procedure for the Google Sheets app (rows, lookups, worksheets, updates, etc.).

When a sheet drives a batch, read every relevant row and the current processing rules before the first write or message. If the task mentions updated rules, check the sheet's policy worksheet and search relevant email and channel messages; use the latest applicable rule from its owner when messages conflict. Match related records by their stable key and required identity fields; inspect duplicate matches instead of using the first match alone.

Decide each row's outcome separately: ordinary action, a specific policy-directed exception action, or no action. Check its status, dates against the task's stated day, start date, notes, linked records, and policy; a headline category alone does not qualify it. Treat notes or linked records that explicitly block processing, such as a hold, return, cancellation, embargo, or inactive recipient, as stop signals even when the row's type otherwise qualifies. If an embargo has no confirmed release, do not infer that it has lifted from the clock alone. A future start does not make later checkpoints active unless the policy calls for a pre-start action. If notes require special handling, check that route before using a default floor or recipient. Do not reinstate a stopped row later without a newer clearance. Carry each decision through every write, notice, count, and summary. A rule that skips all follow-up blocks notes and status changes as well as messages. A skipped row must not receive a routine or substitute notice unless the task or policy explicitly requests one. Send a required exception action to its specified recipient instead of the routine recipient.

Before each action, confirm the row still qualifies and use its own contact and source values. For a summary of processed or qualifying rows, build the list and counts from those rows only; do not mention skipped rows as an aside unless the task requests an exception report. In a policy exception or escalation notice about a row, include its source entity name with its identifier and relevant amount when those fields exist. Preserve exact names, amounts, dates, tracking codes, and policy-defined status labels in records and messages; do not rename a required status with a synonym.

For a batch that sends email or SMS, build a final send list keyed by source row before the first send. Put a row on that list only after every task and policy condition passes, including its date window, current recipient status, notes, and any required evidence from another source. If a rule treats a completion or clearance as changing a row's eligibility, apply that evidence before deciding who receives a message. A non-active recipient or a partner with no payable eligible deals gets no routine notice unless the task or policy explicitly asks for one. Copy the same approved list into every message channel and processed-only summary, with each row's exact destination and required handling details. Check the list for excluded rows once more before sending; a correction or edited summary cannot retract an earlier email or SMS.
